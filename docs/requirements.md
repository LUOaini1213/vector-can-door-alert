# 需求与验收标准

本项目模拟“点火开启且车辆行驶时，车门未关触发告警”。它是自主学习用的 CAN 通信与测试项目；速度阈值和时间参数是本项目制定的教学需求，不代表车厂标定或量产安全要求。

## 统一约定

- 时间单位为整数毫秒。场景事件时间和持续时间必须是非负的 10 ms 整数倍。
- 控制器从 t=0 开始，每 10 ms 计算一次，包括场景结束时刻。
- 同一时刻先接收全部输入，再计算状态；同一 ID 在同一时刻出现多次，按场景顺序接收，最后一帧生效。
- 速度用原始整数比较：5.00 km/h 对应 500，3.00 km/h 对应 300。
- “立即”指当前或下一个 10 ms 计算点生效；不额外增加 200 ms 延时。
- 有效输入保持周期发送时，除非用例特别说明，输入不会因超时影响预期结果。

## 可追踪需求

| 编号 | 需求 | 具体通过条件 |
|---|---|---|
| REQ-01 | 使用三条标准帧 CAN 报文 | VehicleStatus=0x100、DoorStatus=0x101、AlertStatus=0x200；DLC 均为 8。速度在字节 0/1，Intel 小端，分辨率 0.01 km/h。字节布局见 design.md。 |
| REQ-02 | 拒绝无效输入 | 车速范围 0..250.00 km/h；点火字节仅允许 0/1；车门掩码仅允许 0..15。已知输入报文 DLC 错误或字段非法，立即令对应输入流无效，直至收到该 ID 的有效帧。未知 ID 不改变控制状态。 |
| REQ-03 | 按确定的时间顺序运行 | 计算周期 10 ms；同刻先接收再计算；同刻同 ID 最后一帧生效；接收或计算时间倒退应报错。场景时间不在 10 ms 网格上时拒绝执行。 |
| REQ-04 | 初始化显示数据不可用 | 尚未同时收到有效 VehicleStatus 和 DoorStatus 时，warning=0、data_fault=1、reason=1，且不保留触发计时。 |
| REQ-05 | 对每路输入独立判断新鲜度 | 最后有效帧距当前计算点的年龄 <=300 ms 时仍新鲜；310 ms 时超时。任一路缺失、无效或超时，输出 warning=0、data_fault=1、reason=1，并清除触发计时。 |
| REQ-06 | 点火关闭时取消告警 | 两路数据有效且新鲜、ignition=0 时，当前计算点输出 warning=0、data_fault=0、reason=2，清除触发计时。 |
| REQ-07 | 所有车门关闭时取消告警 | 两路数据有效且新鲜、点火开启、door_mask=0 时，当前计算点输出 warning=0、data_fault=0、reason=3，清除触发计时。任意一个低 4 位为 1，均表示至少一扇车门打开。 |
| REQ-08 | 连续满足条件 200 ms 后触发 | 当前未告警，数据有效新鲜、点火开启、车门打开、速度 >=5.00 km/h 时开始计时。经过不足 200 ms：warning=0、reason=5；满 200 ms 的计算点：warning=1、reason=6；data_fault 均为 0。 |
| REQ-09 | 用双阈值实现滞回 | 已告警时，速度 <=3.00 km/h 在当前计算点解除，reason=4；速度 >3.00 km/h 继续告警，reason=6。未告警时，3.00<速度<5.00 不启动告警，reason=4。 |
| REQ-10 | 条件中断后重新计时 | 触发前速度跌至 <5.00 km/h，或出现缺数、无效、超时、点火关闭、全部门关，清除 pending。后续条件恢复时，从新的满足时刻重新等待完整 200 ms；数据恢复不会直接恢复旧告警。 |
| REQ-11 | 状态原因保持唯一且有优先级 | 优先级为数据不可用 > 点火关闭 > 所有门关 > 已告警的滞回处理 > 未告警的触发处理。原因码和输出字节必须一致，定义见 design.md。 |
| REQ-12 | 验证可重复并留下证据 | 场景输入与断言存储在 data/scenarios.json；命令行运行后生成 JSON、HTML、CSV、ASC。断言失败时进程返回非零值；报告保留预期与实际结果、时间序列、输入帧及需求 ID。Python 结果明确标为 Python 仿真结果。 |

## 关键时序例子

下表假设 t=0 同时收到有效车速和车门报文：点火开启、速度 5.00 km/h、左前门打开；两条输入在 0、100、200、300 ms 周期刷新。

| 计算时刻 | warning | data_fault | reason | 解释 |
|---|---:|---:|---:|---|
| 0 ms | 0 | 0 | 5 | 首次满足条件，pending_since_ms=0。 |
| 190 ms | 0 | 0 | 5 | 连续满足 190 ms，尚未到 200 ms。 |
| 200 ms | 1 | 0 | 6 | 满 200 ms，告警开启。 |

如果在 150 ms 收到速度 4.00 km/h，原计时会清除。若在 200 ms 又收到速度 5.00 km/h，且持续维持其他条件，最早在 400 ms 触发。

如果两条输入仅在 t=0 发送一次，则 t=300 ms 仍新鲜，t=310 ms 为数据不可用。不要把“300 ms 还有效”误写成“300 ms 已超时”。

## 证据填写与范围

运行 `python -m door_alert run --scenarios data/scenarios.json --output reports/latest` 后，使用实际生成的报告核对需求覆盖。某需求 ID 出现在场景中，只表示该场景声明覆盖它；还应检查断言是否真正测试了相关边界。

Python 单元测试和场景仿真能验证当前模型、协议及断言的一致性。CANoe 工程导入、CAPL 编译执行、真实 CAN 总线及 ECU 验证，是后续独立的验证阶段；本仓库不会把前一阶段结果作为后一阶段的完成证据。
