# 初学者操作与学习路线

目标是你能从输入帧解释输出，独立改动一个需求并验证结果。仓库代码和文档是学习材料；能运行、能看懂、能独立修改，是三个需要分别验证的阶段。

## 任务一 运行一次并保留输出

在 Windows PowerShell 中进入仓库根目录。以下命令中的 `python` 指可用的 Python 3：

```powershell
python --version
python -m unittest discover -s tests -v
python -m door_alert demo --output reports/demo
python -m door_alert run --scenarios data/scenarios.json --output reports/latest
```

先记录实际的 Python 版本、测试输出、运行日期和报告目录。若出现报错，保留完整错误文字，先定位哪条命令失败，再处理该步骤。测试数量和通过数以你的实际运行结果为准。

打开输出目录内的 HTML 报告，选一个场景，找到输入、断言和时间序列。用自己的话写三句话：输入是什么、预期何时变化、实际是否一致。

本任务完成标准：你能指出一条断言的预期值和实际值，并说明该时间点为什么应当通过。

## 任务二 手算一帧

打开 `docs/design.md` 的报文表，先不用答案完成：

1. 3.00 km/h 的原始整数值是多少？拆成两个小端字节是什么？
2. 右前门和左后门打开时，门掩码是多少？
3. `F4 01 01 00 00 00 00 00` 表示什么车速与点火状态？
4. DoorStatus 第一字节是 0x10，为什么不能当成“所有门关闭”？

做完再运行下面的编码练习：

```python
from door_alert.protocol import encode_vehicle, encode_doors, decode_vehicle

frame = encode_vehicle(0, 5.0, True)
print(hex(frame.arbitration_id))
print(frame.data.hex(" "))
print(decode_vehicle(frame))
print(encode_doors(0, 9).data.hex(" "))
```

先预测四行输出，再执行。核对数值、字节顺序和字典字段；不要只检查有没有报错。

完成标准：不看代码，能解释 0x01F4 为什么在字节流中写为 `f4 01`。

## 任务三 预测时间序列

先在纸上写答案。假设 t=0 速度 5.00 km/h、点火开启、左前门开，两条输入每 100 ms 刷新且持续有效：

| 时间 | 需要预测 |
|---|---|
| 0 ms | warning、reason、pending_since_ms |
| 190 ms | warning、reason |
| 200 ms | warning、reason |

再改条件：所有输入只在 t=0 发一次。预测 t=300 和 t=310 的 warning 与 data_fault。最后在报告中找到对应边界，或在已有场景旁新增一个独立场景验证。

完成标准：能解释“t=0 到 t=190 有 20 个采样点，但只过了 190 ms”。

## 任务四 小步改一个场景

先备份 `data/scenarios.json`，照着已有格式复制一个场景，给它新的 `id`。保留原有用例，不用删除旧断言来获得通过。

建议只改一项：把触发前的速度从 5.00 改成 4.99，其他输入和时间不变。运行前写出哪个断言应该失败、为什么；运行后核对是否如预测。然后把预期改成符合新需求的值，重新执行。

场景中时间必须是非负的 10 ms 整数倍；周期发送的 `until_ms` 包含结束时刻。同刻同 ID 的事件顺序会影响最终输入，新增事件时要检查重复时间。

完成标准：你能区分“实现不符合需求”和“用例预期写错了”，并用输入及时间点说明判断依据。

## 任务五 看懂 Python 的最小路径

按顺序阅读，先不要同时追全部文件：

1. `door_alert/protocol.py`：找到车速从字节变成整数的位置。解释 `低字节 + 高字节 × 256`。
2. `door_alert/controller.py`：找到输入新鲜度检查；再找数据故障、点火关闭、车门关闭、速度判断的分支顺序。
3. 找到 `pending_since_ms`。用一个 t=0 开始、t=150 中断、t=200 重启的例子解释它如何改变。
4. 找到 `data/scenarios.json` 的一条断言，连接到对应的控制器分支和需求 ID。

每次只选择 5–15 行代码：先逐行解释，再预测一个输入，不理解的语法单独做小练习。可以询问 AI，但之后关掉解释，用新数据独立复述和运行。

完成标准：拿到一个以前没见过的输入时序，你能先预测输出，再用程序检查。

## 任务六 学习 CANoe 并记录环境

按 `docs/demo_access.md` 打开 Vector 官方在线演示。先练习识别 Configuration、Trace、信号或测试相关界面，并记录演示中实际存在的窗口名称。

官方在线演示不能上传自定义数据库或数据，因此不能用它完成本仓库 DBC/CAPL 的直接导入验证。获得允许自定义工程的 CANoe 环境后，再执行 `canoe/` 中的集成步骤。

完成标准分两项记录：一是在线演示中亲手操作过的功能；二是本项目是否实际导入、编译和运行。不要把第一项写成第二项。

## 任务七 独立完成一个变更

先选一个变化，例如“告警触发延时从 200 ms 改为 300 ms”。写下受影响的需求、代码位置、边界用例和预期结果，再进行修改。至少覆盖 290/300 ms 触发边界，以及中断后重新计时。

如果时间达到输入超时边界，先确认用例里两路输入有周期刷新，避免把超时导致的未告警误认为延时逻辑正确。

完成后保存一段自己的讲解：原行为、改动理由、如何验证、实际结果。能完成这一步，才适合在面试中说自己修改并验证过该功能。

## 自测答案 先做再看

- 3.00 km/h 对应 300，即 0x012C，小端字节 `2c 01`。
- 右前门 bit 1 与左后门 bit 2：掩码为 2+4=6，即 0x06。
- `F4 01` 对应 500，物理速度 5.00 km/h；点火字节 01 表示开启。
- 0x10 设置了保留高位，输入非法，需要报数据不可用。
- 持续有效刷新时：t=0 开始计时、reason=5；t=190 仍未告警；t=200 告警、reason=6。
- 只在 t=0 收到两帧时：t=300 仍新鲜；t=310 超时，warning=0、data_fault=1。
