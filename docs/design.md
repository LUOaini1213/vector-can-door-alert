# 设计与信号说明

## 从场景到模块

```text
data/scenarios.json
    -> 生成或注入带时间戳的 CAN 帧
    -> protocol 解码和字段检查
    -> controller 接收、判断新鲜度、每 10 ms 计算
    -> Snapshot 与 AlertStatus
    -> 断言比较、JSON / HTML / CSV / ASC 报告
```

Python 路径用于本机可重复验证。`canoe/` 中的 CAPL 源文件用于后续导入 CANoe 环境；在真实导入、编译和运行前，其状态是待集成验证。

## 三条报文布局

全部采用 Classic CAN、11 位标准 ID、DLC 8；字节从 0 开始计数。多字节数值使用 Intel 小端：低字节在前。

| 报文 | ID | 字节或位 | 含义 | 有效值 |
|---|---|---|---|---|
| VehicleStatus | 0x100 | byte 0..1 | speed_raw，物理速度=speed_raw×0.01 km/h | 0..25000，对应 0..250.00 km/h |
| VehicleStatus | 0x100 | byte 2 | ignition | 0=关闭；1=开启 |
| VehicleStatus | 0x100 | byte 3..7 | 未使用 | 编码器填 0；输入判定不依赖这些字节 |
| DoorStatus | 0x101 | byte 0 bit 0 | 左前门 FL | 0=关；1=开 |
| DoorStatus | 0x101 | byte 0 bit 1 | 右前门 FR | 0=关；1=开 |
| DoorStatus | 0x101 | byte 0 bit 2 | 左后门 RL | 0=关；1=开 |
| DoorStatus | 0x101 | byte 0 bit 3 | 右后门 RR | 0=关；1=开 |
| DoorStatus | 0x101 | byte 0 bit 4..7 | 保留位 | 必须全为 0；否则输入无效 |
| DoorStatus | 0x101 | byte 1..7 | 未使用 | 编码器填 0；输入判定不依赖这些字节 |
| AlertStatus | 0x200 | byte 0 | warning | 0=未告警；1=告警 |
| AlertStatus | 0x200 | byte 1 | data_fault | 0=输入可用；1=输入不可用 |
| AlertStatus | 0x200 | byte 2 | reason | 下表定义的 1..6 |
| AlertStatus | 0x200 | byte 3..7 | 未使用 | 输出固定为 0 |

编码例子：速度 5.00 km/h、点火开启时，VehicleStatus 的数据是 `F4 01 01 00 00 00 00 00`。因为 5.00 / 0.01=500，而 500 的十六进制是 0x01F4；低字节 F4 先发送。

左前门与右后门同时打开，门掩码是二进制 `1001`，即十六进制 0x09。CANoe 的 DBC 使用相同布局，导入后应逐项核对报文 ID、DLC、起始位、长度、字节序、比例和取值范围。

## 输入流与有效性

控制器分别记录 VehicleStatus 和 DoorStatus 的值、最后有效接收时间和当前是否有效。一条已知输入报文格式错误，会令它自己的输入流无效；另一条输入流的有效状态不能代替它。有效同 ID 报文到达后，该流重新有效并刷新时间。

输入可用的条件是：已有有效接收时间、当前流有效、当前时间减最后有效时间 <=300 ms。未知 ID 不参与控制逻辑。收到一条非法帧后，即使它距离上一条有效帧还不到 300 ms，也不能继续使用旧值当作有效输入。

同刻所有帧先接收，随后计算。若同一 ID 在同一时刻先有效、后非法，最终为无效；若先非法、后有效，最终为有效。此规则用于明确解释重复或矛盾输入。

## 状态优先级与原因码

从上往下命中第一项后就结束本次计算。

| 优先级 | 条件 | warning | data_fault | reason |
|---:|---|---:|---:|---|
| 1 | 任一输入缺失、无效或超时 | 0 | 1 | 1 DATA_UNAVAILABLE |
| 2 | 两路可用，但点火关闭 | 0 | 0 | 2 IGNITION_OFF |
| 3 | 两路可用、点火开启，但全部门关 | 0 | 0 | 3 DOORS_CLOSED |
| 4 | 已告警，车速 <=3.00 km/h | 0 | 0 | 4 BELOW_THRESHOLD |
| 4 | 已告警，车速 >3.00 km/h | 1 | 0 | 6 WARNING_ACTIVE |
| 5 | 未告警，车速 <5.00 km/h | 0 | 0 | 4 BELOW_THRESHOLD |
| 5 | 未告警，车速 >=5.00 km/h，持续不足 200 ms | 0 | 0 | 5 DEBOUNCING |
| 5 | 未告警，车速 >=5.00 km/h，持续已满 200 ms | 1 | 0 | 6 WARNING_ACTIVE |

因此，“点火关闭且门关”得到 reason=2；“点火关闭且车门流超时”得到 reason=1。原因码说明本次计算采用的首要分支，不能从一个原因码反推其他所有输入一定满足哪种状态。

## 200 ms 延时与滞回

200 ms 去抖用于避免极短的开启条件立即触发告警。它计算的是时间差，不能简单把“连续 20 个采样值”当作 200 ms：从 t=0 到 t=190 的 20 个计算点只跨过了 190 ms；满 200 ms 的点是 t=200。

触发前，3.00<速度<5.00 会取消计时。告警已经开启后，同样的速度区间会保持告警；这就是滞回，它避免车速在单一阈值附近波动时频繁开关。

示例假设点火持续开启、门持续打开，且两路输入始终有效新鲜：

| 时刻 | 输入变化 | 结果 |
|---|---|---|
| 0 ms | 速度 5.00 | 开始计时，warning=0。 |
| 200 ms | 速度仍为 5.00 | 告警开启，warning=1。 |
| 210 ms | 速度变为 4.00 | 保持告警。 |
| 220 ms | 速度变为 3.00 | 告警解除。 |
| 230 ms | 速度变为 4.00 | 保持未告警，不计时。 |
| 240 ms | 速度变为 5.00 | 重新开始 200 ms 计时。 |
| 440 ms | 条件持续满足 | 再次告警。 |

关闭所有车门、关闭点火或数据不可用的优先级高于速度滞回，均会清除告警和未完成的触发计时。

## 可观察数据

每个计算点记录 `timestamp_ms`、`warning`、`data_fault`、`reason`、`speed_kmh`、`door_mask`、`pending_since_ms`。前四项直接支持输出断言，后三项帮助解释边界时刻和计时重启。报告中的输入帧可用于复核原始字节，不应只依据最后一行“通过”判断模型正确。

## 后续 CANoe 集成核对

1. 按 `canoe/` 内说明创建或配置网络，导入仓库 DBC。
2. 编译 CAPL，先修正所有编译错误，再运行单一正常场景。
3. 对照同一输入时序，比较 CANoe 输出与 Python 的关键时间点，尤其是 190/200 ms、300/310 ms、3.00/5.00 km/h。
4. 留存配置版本、CAPL 编译结果、Trace 与测试结果，并记录任何差异及原因。

ASC 文件可以辅助观察或回放；能否直接用于某个 CANoe 版本的回放，需按实际版本和通道配置验证。仅生成 ASC 文件不构成 CANoe 已运行的证据。
